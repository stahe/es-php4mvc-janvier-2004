    2. Un enfoque de desarrollo MVC para Web/PHP

    Aquí proponemos un enfoque para desarrollar aplicaciones web/PHP que sigan la arquitectura MVC. Su único objetivo es servir de punto de partida. El lector deberá adaptarlo a sus propias preferencias y necesidades.

    1. Comenzaremos definiendo todas las vistas de la aplicación. Estas son las páginas web que se muestran al usuario. Adoptaremos la perspectiva del usuario al diseñar las vistas. Hay tres tipos de vistas:
      • el formulario de entrada, diseñado para recopilar información del usuario. Suele incluir un botón para enviar la información introducida al servidor.
      • La página de respuesta, que solo sirve para proporcionar información al usuario. A menudo incluye uno o más enlaces que permiten al usuario continuar utilizando la aplicación en otra página.
      • la página mixta: el controlador ha enviado al cliente una página que contiene información generada por él. El cliente utilizará esta misma página para proporcionar al controlador nueva información del usuario.
    1. Cada vista generará una página PHP. Para cada una de ellas:
      • diseñaremos el diseño de la página
      • determinaremos qué partes de ella son dinámicas:
        • la información destinada al usuario que debe proporcionar el controlador como parámetros a la vista PHP. Una solución sencilla es la siguiente:
          • El controlador coloca la información que desea proporcionar a una vista V en un diccionario $dResponse
          • El controlador muestra la vista V. Si esta corresponde al archivo fuente V.php, esta visualización se consigue simplemente mediante la instrucción include V.php.
          • La inclusión anterior es una inclusión de código dentro del controlador. El código de V.php puede acceder directamente al diccionario $dResponse rellenado por el controlador.
        • Los datos de entrada que deben transmitirse al programa principal para su procesamiento. Estos datos deben formar parte de un formulario HTML (etiqueta <form>).
    1. Podemos esquematizar la E/S para cada vista
    • Las entradas son los datos que el controlador debe proporcionar a la página PHP
    • Las salidas son los datos que la página PHP debe proporcionar al controlador de la aplicación. Forman parte de un formulario HTML, y el controlador los recuperará mediante una operación como $_GET["param"] (método GET) o $_POST["param"] (método POST).
    1. A menudo, la página final enviada al cliente no es una sola vista, sino una composición de vistas. Por ejemplo, la página enviada a un usuario podría tener este aspecto:

    El área 1 puede ser un banner de cabecera, el área 2 un banner de menú y el área 3 un área de contenido. En PHP, esta composición se puede lograr utilizando el siguiente código HTML/PHP:

    <table>
    <tr>
        <td><?php include zone1.php ?></td>
    </tr>
    <tr>
        <td><?php include zone2.php ?></td>
        <td><?php include zone3.php ?></td>
    </tr>
</table>

    Puedes hacer que este código sea dinámico escribiendo:

    <table>
    <tr>
        <td><?php include $dReponse['urlZone1'] ?></td>
    </tr>
    <tr>
        <td><?php include $dReponse['urlZone2'] ?></td>
        <td><?php include $dReponse['urlZone3'] ?></td>
    </tr>
</table>

    Esta composición de vista puede ser el único formato de la respuesta enviada al usuario. En este caso, cada respuesta al cliente debe establecer las tres URL que se cargarán en las tres zonas antes de mostrar la página de respuesta. Podemos generalizar este ejemplo imaginando que existen varias plantillas posibles para la página de respuesta. Por lo tanto, la respuesta al cliente debe:

    • determinar la plantilla que se va a utilizar
    • determinar los elementos que se deben incluir en ella
    • solicitar la visualización de la plantilla
    1. Escribiremos el código PHP/HTML para cada plantilla de respuesta. Su código suele ser sencillo. El código para el ejemplo anterior podría ser: 
    <?php
    // initializations for testing without a controller
...
?>
<html>
    <head>
      <title><?php echo $dReponse['titre'] ?></title>
      <link type="text/css" href="<?php echo $dReponse['style']['url'] ?>" rel="stylesheet" />    
    </head>
  <body>      
    <table>
        <tr>
            <td><?php include $dReponse['urlZone1'] ?></td>
        </tr>
        <tr>
            <td><?php include $dReponse['urlZone2'] ?></td>
            <td><?php include $dReponse['urlZone3'] ?></td>
        </tr>
    </table>
  <body>
</html>

    Siempre que sea posible, utilizaremos una hoja de estilo para poder cambiar el «aspecto» de la respuesta sin tener que modificar el código PHP/HTML.

    1. Escribiremos el código PHP/HTML para cada vista básica. Por lo general, tendrá la siguiente forma: 
    <?php
     // a few initializations may be necessary, particularly in the debugging phase
    ...
?>

<balise>
...
         // here we'll try to minimize the php code
</balise>

    Ten en cuenta que una vista básica está incrustada dentro de una plantilla. Su código HTML está integrado en el código de la plantilla. En la mayoría de los casos, la plantilla ya incluye las etiquetas <html>, <head> y <body>. Por lo tanto, es raro encontrar estas etiquetas en una vista básica.

    1. Podemos pasar a probar las distintas plantillas de respuesta y vistas básicas
    • Se prueba cada plantilla de respuesta. Si una plantilla se llama modele1.php, solicitaremos la URL http://localhost/chemin/modele1.php mediante un navegador. La plantilla espera valores del controlador. En este caso, la llamamos directamente en lugar de a través del controlador. La plantilla no recibirá los parámetros esperados. Para poder realizar la prueba de todos modos, inicializaremos manualmente los parámetros esperados en la página PHP de la plantilla utilizando constantes.
    • Se prueban todos los modelos, así como todas las vistas básicas. Este es también el momento de desarrollar los primeros elementos de las hojas de estilo utilizadas.
    1. A continuación, escribimos la lógica de la aplicación:
    • El controlador, o programa principal, suele gestionar varias acciones. La acción que se va a realizar debe definirse en las solicitudes que recibe. Esto se puede hacer utilizando un parámetro de solicitud, que aquí llamaremos `action`:
      • si la solicitud proviene de un formulario (<form>), este parámetro puede ser un parámetro oculto del formulario: 
    <form ... action="/C/main.php" method="post"  ...>
<input type="hidden" name="action" value="uneAction">
...
</form>
    • (continuación)
      • Si la solicitud proviene de un enlace, puedes configurarlo de la siguiente manera: 
     <a href="/C/main.php?action=uneAction">lien</a>

    El controlador puede comenzar leyendo el valor de este parámetro y, a continuación, delegar el procesamiento de la solicitud a un módulo encargado de gestionar este tipo de solicitudes. En este caso, hemos supuesto que todo está controlado por un único script llamado main.php. Si la aplicación necesita gestionar las acciones action1, action2, ..., actionx, puedes crear una función para cada acción dentro del controlador. Si hay muchas acciones, esto puede dar lugar a un controlador «dinosaurio». Como alternativa, se pueden crear scripts action1.php, action2.php, ..., actionx.php encargados de gestionar cada acción. El controlador encargado de gestionar la acción actionx simplemente cargará el código del script correspondiente utilizando una instrucción como include "actionx.php". La ventaja de este método es que se trabaja fuera del código del controlador. De este modo, cada miembro del equipo de desarrollo puede trabajar en el script que gestiona una acción actionx de forma relativamente independiente. Incluir el código del script actionx.php en el código del controlador en tiempo de ejecución también tiene la ventaja de reducir la cantidad de código cargado en la memoria. Solo se carga el código para gestionar la acción actual. Esta inclusión de código implica que las variables del controlador pueden entrar en conflicto con las del script de la acción. Veremos que podemos limitar las variables del controlador a unas pocas bien definidas, que luego deberían evitarse en los scripts.

    • Buscaremos sistemáticamente aislar la lógica de negocio o el código para acceder a datos persistentes en módulos separados. El controlador actúa como una especie de jefe de equipo que recibe solicitudes de sus clientes (clientes web) y hace que las ejecuten las entidades más adecuadas (los módulos de negocio). Al escribir el controlador, determinaremos la interfaz de los módulos de negocio que se van a escribir. Esto se aplica si es necesario crear dichos módulos de negocio. Si ya existen, el controlador se adaptará a la interfaz de estos módulos existentes.
    1. Escribiremos el esqueleto de los módulos de negocio que requiere el controlador. Por ejemplo, si el controlador utiliza un módulo `getCodes` que devuelve una matriz de cadenas, inicialmente podemos escribir simplemente: 
    function getCodes(){
    return array("code1","code2","code3");
}
    1. A continuación, podemos pasar a probar el controlador y los scripts PHP asociados:
    • El controlador, los scripts de acción, los modelos, las vistas y los recursos que requiere la aplicación (imágenes, etc.) se colocan en la carpeta DC asociada al contexto C de la aplicación.
    • Una vez hecho esto, se prueba la aplicación y se corrigen los errores iniciales. Si main.php es el controlador y C es el contexto de la aplicación, solicitaremos la URL http://localhost/C/main.php. Al final de esta fase, la arquitectura de la aplicación está operativa. Esta fase de pruebas puede resultar complicada, dado que hay pocas herramientas de depuración disponibles si no se utilizan entornos de desarrollo avanzados, que suelen ser de pago. Se pueden utilizar sentencias echo "mensaje", que escriben en el flujo HTML enviado al cliente y, por lo tanto, aparecen en la página web mostrada por el navegador.
    1. Por último, escribimos las clases de negocio requeridas por el controlador. Esto suele implicar el desarrollo estándar de una clase PHP, que normalmente es independiente de cualquier aplicación web. Primero se probará fuera de este entorno, utilizando una aplicación de consola, por ejemplo. Una vez escrita una clase de negocio, la integramos en la arquitectura de implementación de la aplicación web y comprobamos su correcta integración.
